# AI Editorial Office — прототип автоматической AI-редакции

Интерактивный прототип редакционного контура, в котором AI-агенты принимают свободную команду, находят информационные поводы, готовят материалы и передают редактору только те решения, которые требуют человеческого контроля.

Этот репозиторий используется как **образец интерфейса и контрактов для будущего MVP**. Он показывает целевой пользовательский процесс и границы ответственности между UI, API, оркестратором и редактором, но пока не является production-системой.

## Что проверяет прототип

- подачу свободной команды без ручного выбора типа задачи;
- серверное определение типа, подтипа, глубины и платформ;
- очередь редакционных задач и их состояния;
- результаты агентов, утверждения, черновики и историю обработки;
- подготовку публикационных пакетов для разных платформ;
- готовность пакета с визуалом и без визуала;
- решения редактора: одобрить, вернуть на доработку, отклонить, запланировать;
- радар сигналов, календарь, источники, цели публикации и запросы редактору;
- обработку ошибок и подтверждение необратимых действий;
- соответствие интерфейса контракту S09.

## Основной принцип

Интерфейс не управляет редакционным процессом самостоятельно. Он отображает решения сервера и отправляет только явно выбранные действия редактора.

В частности:

- кнопки действий приходят из `available_actions`;
- готовность пакета приходит из `ready_for_review`;
- причины блокировки приходят из `blocking_reasons`;
- UI не отправляет `current_state`;
- UI не меняет `content_origin`;
- UI не вычисляет переходы состояний;
- все изменения выполняются через `POST`;
- `PUT`, `PATCH` и `DELETE` в контракте прототипа не используются.

## Что входит в пользовательский контур

### Э‑9. Подача команды

Редактор вводит команду обычным текстом и при необходимости добавляет метаданные вложения. Выбирать тип задачи, глубину обработки или площадку вручную не нужно — это определяет `ORCHESTRATOR`.

В MVP содержимое файлов не передаётся. Используются только:

- `attachment_kind`;
- `original_filename`;
- `mime_type`;
- `size_bytes`;
- `source_uri`.

### Э‑1. Очередь задач

Показывает задачи, их текущее состояние, платформы и количество действий, разрешённых API.

### Э‑2. Карточка задачи

Объединяет результаты агентов, утверждения, черновики, пакеты, визуалы, календарные слоты, историю и попытки публикации.

### Э‑3. Радар

Показывает прогоны мониторинга, найденные сигналы и связи с возможными дубликатами.

### Э‑4. Пакет к рассмотрению

Показывает готовые и заблокированные публикационные пакеты. Пакет может быть готов без изображения, если сервер вернул:

```text
visual_status = NOT_REQUIRED
visual_not_required = true
```

### Э‑5. Решения редактора

Поддерживает подтверждаемые действия:

- одобрить;
- вернуть на доработку;
- отклонить;
- запланировать;
- запросить публикацию;
- ответить на запрос;
- изменить приоритет;
- одобрить класс источника;
- перевести цель публикации в production-режим.

Для повторяемых критичных операций используется `Idempotency-Key`.

### Э‑6–Э‑8. Рабочие справочники

Прототип также показывает календарь, источники, цели публикации и запросы, требующие решения редактора.

## Что работает сейчас

- React-интерфейс со всеми основными экранами;
- локальный mock API с префиксом `/api/v1`;
- коллекционные и error-конверты контракта S09;
- GET/POST-маршруты;
- интерактивные решения и изменения состояния в памяти вкладки;
- точные ошибки подачи команды:
  - `EMPTY_COMMAND`;
  - `NO_USABLE_COMMAND_CONTENT`;
  - `ATTACHMENT_CONTENT_NOT_ACCEPTED`;
- примеры готового и заблокированного пакета без визуала;
- таблица «экран → операции API»;
- сравнение поведения кнопок в прототипе и production-системе;
- тексты подтверждений необратимых действий;
- список контрактных неопределённостей и мест с прочерками.

## Что намеренно не реализовано

Это контрактный UI-прототип. В нём нет:

- настоящего backend API;
- базы данных и постоянного хранения;
- авторизации и ролей;
- реальных AI-моделей и агентов;
- фоновых очередей и планировщика;
- загрузки и хранения файлов;
- подключения Telegram, VK или других каналов;
- реальной публикации;
- production-мониторинга и аудита.

Операция публикации остаётся заглушкой и возвращает `STUB_NOT_IMPLEMENTED`. Ни одно действие в прототипе не публикует материалы во внешние каналы.

## Архитектура

```text
React components
       │
       ▼
src/api/client.ts
       │
       ▼
src/api/mock-server.ts
       │
       ├── contracts.ts
       └── fixtures.ts
```

Все компоненты обращаются к данным через единый клиентский модуль:

```text
artifacts/ai-editorial-office/src/api/client.ts
```

Прямой доступ компонентов к фикстурам или mock-серверу не допускается.

### Ключевые файлы

| Путь | Назначение |
|---|---|
| `artifacts/ai-editorial-office/src/api/contracts.ts` | Типы, перечисления и конверты S09 |
| `artifacts/ai-editorial-office/src/api/fixtures.ts` | Контрактные mock-данные |
| `artifacts/ai-editorial-office/src/api/mock-server.ts` | GET/POST-маршрутизация и ошибки |
| `artifacts/ai-editorial-office/src/api/client.ts` | Единая точка доступа UI к API |
| `artifacts/ai-editorial-office/src/api/operations-table.ts` | Таблица операций и материалы контрактной проверки |
| `artifacts/ai-editorial-office/src/App.tsx` | Экраны и пользовательские сценарии |

## Рекомендуемый сценарий демонстрации

1. Открыть «Подать команду».
2. Отправить текстовую команду и показать результат `TASK_CREATED`.
3. Отправить пустую команду и показать `EMPTY_COMMAND`.
4. Добавить метаданные `IMAGE` без текста и показать `NO_USABLE_COMMAND_CONTENT`.
5. Открыть очередь и карточку задачи.
6. Показать, что набор кнопок зависит только от `available_actions`.
7. Открыть пакет к рассмотрению.
8. Сравнить:
   - готовый пакет с визуалом;
   - готовый пакет с `NOT_REQUIRED`;
   - пакет, заблокированный причиной `VISUAL_PACKAGE_MISSING`.
9. Выполнить решение редактора и показать обязательное подтверждение.
10. Открыть экран «Контракт» с таблицей API-операций и известными неопределённостями.

## Как использовать прототип при разработке MVP

Рекомендуемый порядок замены mock-слоя:

1. Зафиксировать OpenAPI-контракт на основе `contracts.ts`.
2. Реализовать production API с теми же URL, методами и конвертами.
3. Сохранить `client.ts` как единственную точку доступа интерфейса к API.
4. Заменить транспорт mock-клиента на HTTP без переноса бизнес-логики в UI.
5. Добавить авторизацию, роли и серверный аудит решений.
6. Подключить постоянное хранилище, очередь задач и `ORCHESTRATOR`.
7. Реализовать адаптеры AI-агентов и внешних публикационных каналов.
8. Добавить наблюдаемость, повторные попытки и защиту от дублирующих операций.

## Критерии сохранения совместимости

При развитии MVP важно сохранить:

- один клиентский API-слой для UI;
- сервер как единственный источник допустимых действий;
- сервер как единственный источник готовности пакета;
- неизменяемый журнал команд и редакторских решений;
- идемпотентность критичных POST-операций;
- явные подтверждения необратимых действий;
- отображение неизвестных значений прочерком, без домысливания;
- разделение production-поведения и временных mock-эффектов.

## Статус проекта

Проект предназначен для проверки пользовательских сценариев, согласования API-контракта и постановки задач на MVP.

**Не использовать как production-систему и не подключать к реальным каналам публикации без реализации backend, безопасности, аудита и эксплуатационных механизмов.**
